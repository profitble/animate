# Supabase Media Archive Setup Instructions

## Goal

Set up a Supabase Storage + Postgres system for archiving generated Animate-model input pairs.

Each media pair contains:

* one image input
* one video input

The local files are currently numbered for human workflow convenience, like:

```txt
10-videos/
├── 1/
│   ├── 1.jpeg
│   └── 1.mp4
├── 2/
│   ├── 2.jpeg
│   └── 2.mp4
```

Do **not** preserve the numeric names in Supabase Storage.

Instead, each image/video pair should be converted into a stable 8-character hash folder.

---

## Desired Supabase Storage Structure

Create one Storage bucket:

```txt
media-archive
```

Inside the bucket, use this path format:

```txt
raw/{archive_date}/{pair_code}/image.jpeg
raw/{archive_date}/{pair_code}/video.mp4
```

Example:

```txt
media-archive/
└── raw/
    └── 2026-06-12/
        ├── a8f4c91e/
        │   ├── image.jpeg
        │   └── video.mp4
        ├── 91bd02aa/
        │   ├── image.jpeg
        │   └── video.mp4
        └── f03ac219/
            ├── image.jpeg
            └── video.mp4
```

Do **not** create extra folders like:

```txt
batch-10/
pair-000001/
D1-archive/
D2-archive/
```

Use real dates instead of `D1`, `D2`, etc.

---

## Naming Rules

### Folder Name

Each image/video pair gets one shared `pair_code`.

The `pair_code` should be an 8-character lowercase hex string.

Example:

```txt
a8f4c91e
```

The pair code should be generated from the content hash of the image and video together.

Recommended logic:

```txt
pair_code = first 8 chars of sha256(image_sha256 + video_sha256)
```

Both files live inside the same hash folder:

```txt
raw/2026-06-12/a8f4c91e/image.jpeg
raw/2026-06-12/a8f4c91e/video.mp4
```

### File Names

Inside the hash folder, always use canonical names:

```txt
image.jpeg
video.mp4
```

Do not use:

```txt
1.jpeg
1.mp4
2.jpeg
2.mp4
```

The original local number should be stored in the database, not in the storage path.

---

## Create Storage Bucket

Create a Supabase Storage bucket named:

```txt
media-archive
```

Recommended setting:

```txt
private bucket
```

Reason:

The files may be used by Modal, but they do not need to be permanently public.

Modal should receive temporary signed URLs generated by the backend.

If signed URLs are too annoying during early testing, the bucket can temporarily be public, but private is the safer default.

---

## Create Postgres Table

Run this SQL:

```sql
create extension if not exists pgcrypto;

create table if not exists public.media_archive_items (
  id uuid primary key default gen_random_uuid(),

  archive_date date not null,

  local_root text,
  local_index integer not null,

  pair_code char(8) not null,

  image_original_filename text not null,
  video_original_filename text not null,

  image_storage_path text not null,
  video_storage_path text not null,

  image_sha256 text not null,
  video_sha256 text not null,
  pair_sha256 text not null,

  image_mime_type text default 'image/jpeg',
  video_mime_type text default 'video/mp4',

  image_size_bytes bigint,
  video_size_bytes bigint,

  status text not null default 'uploaded',

  notes text,

  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),

  constraint media_archive_items_pair_code_unique unique (pair_code),
  constraint media_archive_items_image_path_unique unique (image_storage_path),
  constraint media_archive_items_video_path_unique unique (video_storage_path),
  constraint media_archive_items_status_check check (
    status in ('uploaded', 'processing', 'processed', 'failed', 'archived')
  )
);
```

---

## Create Indexes

Run this SQL:

```sql
create index if not exists media_archive_items_archive_date_idx
on public.media_archive_items (archive_date desc);

create index if not exists media_archive_items_local_index_idx
on public.media_archive_items (local_index);

create index if not exists media_archive_items_status_idx
on public.media_archive_items (status);

create index if not exists media_archive_items_created_at_idx
on public.media_archive_items (created_at desc);
```

---

## Add Updated At Trigger

Run this SQL:

```sql
create or replace function public.set_updated_at()
returns trigger as $$
begin
  new.updated_at = now();
  return new;
end;
$$ language plpgsql;

drop trigger if exists set_media_archive_items_updated_at
on public.media_archive_items;

create trigger set_media_archive_items_updated_at
before update on public.media_archive_items
for each row
execute function public.set_updated_at();
```

## Expected Upload Logic

For every local folder like:

```txt
10-videos/1/
```

Read:

```txt
10-videos/1/1.jpeg
10-videos/1/1.mp4
```

Then:

1. Hash the image file.
2. Hash the video file.
3. Combine both hashes.
4. Generate an 8-character `pair_code`.
5. Upload both files to Supabase Storage.
6. Insert one database row into `media_archive_items`.

Example final paths:

```txt
raw/2026-06-12/a8f4c91e/image.jpeg
raw/2026-06-12/a8f4c91e/video.mp4
```

Example database row:

```txt
archive_date: 2026-06-12
local_root: 10-videos
local_index: 1
pair_code: a8f4c91e
image_original_filename: 1.jpeg
video_original_filename: 1.mp4
image_storage_path: raw/2026-06-12/a8f4c91e/image.jpeg
video_storage_path: raw/2026-06-12/a8f4c91e/video.mp4
status: uploaded
```

---

## Collision Rule

Because the folder name is only 8 characters, collisions are possible.

Before inserting a new row:

1. Check whether `pair_code` already exists.
2. If it exists and the `pair_sha256` is the same, treat it as already uploaded.
3. If it exists but the `pair_sha256` is different, use the first 10 or 12 characters of the hash instead, or regenerate a longer code.

For now, the table uses `char(8)` because the requested system is 8 characters.

If long-term scale matters, change this to:

```sql
pair_code text not null
```

and allow 12-character codes.

---

## Do Not Overwrite Files

Uploads should never overwrite existing files.

Use upload behavior equivalent to:

```txt
upsert: false
```

If the object already exists, skip upload and verify the database row instead.

---

## Modal Integration

Modal should not receive local file paths.

Modal should receive either:

1. signed Supabase URLs, if bucket is private
2. public Supabase URLs, if bucket is public during testing

The app/backend should look up a `media_archive_items` row, generate URLs for:

```txt
image_storage_path
video_storage_path
```

Then pass those URLs into Modal.

---

## Recommended Query for Getting Today’s Uploaded Pairs

```sql
select
  id,
  archive_date,
  local_index,
  pair_code,
  image_storage_path,
  video_storage_path,
  status,
  created_at
from public.media_archive_items
where archive_date = current_date
order by local_index asc;
```

---

## Recommended Query for Finding a Local Number

```sql
select *
from public.media_archive_items
where archive_date = '2026-06-12'
  and local_index = 1;
```

---

## Recommended Query for Getting Unprocessed Items

```sql
select *
from public.media_archive_items
where status = 'uploaded'
order by created_at asc;
```

---

## Summary

The final system should be:

```txt
Supabase Storage = actual image/video files
Postgres table = source of truth / manifest
pair_code = stable hash folder that connects image + video
local_index = original human number from local folder
archive_date = replacement for D1, D2, D3
```

The storage structure should stay flat and simple:

```txt
raw/2026-06-12/a8f4c91e/image.jpeg
raw/2026-06-12/a8f4c91e/video.mp4
```

No batch folders.

No pair folders.

No numeric public filenames.

No deleting old media just because the local machine is full.
